# 文件包命名与每周终止清理

本导出包不附带任何用户的删除授权。下列清理流程只在当前用户已明确授权对应范围时执行，否则仅输出计划。本规则取代旧规则中同范围的逐次清理确认门及“HR无回应仍永久保留材料”的规定。发送消息和投递授权不受本规则影响。

## 名称与定位

- 所有单岗位定向简历、快速补强、公司情报、面试材料包使用 `岗位编号_公司_具体岗位名称`。正式根目录保持 `data/application_packages`。
- 编号和资产ID永久稳定。公司、职位取唯一台账；台账缺失时仅可按包内明确元信息更名，不推断清理资格。
- 用 `discover-brand-roles/scripts/package_policy.py` 的 `package_name` 规范 Windows 非法字符。完整岗位名保留；名称过长时使用已核实的公司简称，不静默截断具体岗位。路径过长则报告该包阻塞。
- 定位时先读索引中的实际路径，再精确校验目录名中首个下划线前的岗位编号；兼容旧纯编号目录。禁止模糊前缀匹配。旧名与新名并存时先核对，不新建第三个包。
- 更名需要同步台账、资产索引、Markdown导航、包内引用和实际超链接。重命名不改Word正文、稳定编号或投递历史。正式登记、路径存在性和保留文件哈希全部通过后才完成。

## 清理条件

每周用户确认/调整台账后及现有职位雷达每次运行时，读取已保存的唯一台账；先处理终止清理，再处理活跃岗位生成。使用 `cleanup_reason` 判断：

1. 状态精确为 `已失效` 或 `HR无回应或失联`，可清理该岗位全部生成材料，既往投递历史不再阻塞此授权。
2. 用户已标灰且状态为 `深度评估后不投`、`已结束`、`HR明确拒绝/不合适`，或结束原因为 `用户确认不投` 的相应终态，可清理。
3. 原系统核验猎头终止入口继续适用，仍核对招聘主体、企业方核验及原协议的无投递历史条件。
4. `用户保留`、`已投递—待反馈`、`面试中`及其他活跃状态，绿色待吸收反馈、明确保留材料指令优先保护。灰色与活跃状态冲突时暂不删除并报告。
5. 自动 Skip、待核实、页面打不开、疑似关闭、仅因投递后经过若干天都不是清理依据。不得自行设置 HR 无回应天数，也不得把它们自动改成失效。

本次授权覆盖终止岗位的当前简历、英文稿、审阅稿、快速补强、公司岗位情报、面试准备及可精确归属的历史/暂存生成副本。保留台账主记录、完整JD/快照、来源、判断、投递及沟通历史、风险、原状态和结束原因；必要历史事实先补入该行。原始简历、岗位族底稿、完整能力库、经历证据库、其他岗位文件与 `sources/` 始终保护。混合目录只逐个处理精确核对的生成文件，不能整目录删除。

## 执行与验收

1. 只读审计台账、索引、状态颜色、实际文件，生成包含岗位编号、原/新绝对路径、动作、原因、相对文件路径、大小和SHA-256的清单。原始资料目录和重解析点不得进入清单。
2. 关闭台账/索引占用后重新读取最新文件并核对哈希。无人值守遇锁时记录待处理清单并下次重试，不覆盖未保存编辑，也不宣称已清理。
3. 更名先暂存引用更新，核验后变更目录与两本正式工作簿。清理用 `cleanup_gray_job_materials.py plan` → 核验 → `apply`；每个待删目录的父目录必须明确获准，每次执行前重核台账和文件清单。有变化即阻塞该岗位。
4. 删除同岗位索引中层级以 `单岗位` 开头的资产记录。台账只清空已删除材料的引用/超链接，不删岗位行，不清掉投递渠道、日期、反馈或历史判断。下一步写“终止岗位材料已清理；仅保留台账历史，重新开启后按需生成”。备注记录日期、清理原因、原资产ID与实际删除数量；幂等运行不重复追加同一回执。
5. 临时事务备份只用于本次失败恢复；成功并回读后删除材料备份及临时副本。长期只保留台账历史和轻量审计清单，不换个目录继续长期保存已清理材料。失败保留恢复所需文件并明确说明。
6. 回读验证台账岗位数/ID/历史字段不丢失，索引只移除指定资产，活动包路径可访问，灰色冲突未删除，源目录消失，所有保留文件哈希与清单一致；重复运行应为零删除/零更名。筛选、状态下拉、表结构和格式保持。

比较过逐状态直接删除与现有清单重核流程；采用后者，复用本机已有实现，无需新增第三方清理依赖。Windows命名约束参考 https://learn.microsoft.com/zh-cn/windows/win32/fileio/naming-a-file ，目录删除边界参考 https://docs.python.org/3/library/shutil.html 。
