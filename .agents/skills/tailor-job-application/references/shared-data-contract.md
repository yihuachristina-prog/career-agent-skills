# 共享求职数据契约

两个 Skill 必须使用同一组持久化资产。按文件名在用户的持久文件中查找；找到后保留文件身份并更新原文件，不得创建同名平行副本。

| 资产 | 唯一职责 |
|---|---|
| `候选人画像与薪资边界.md` | 城市、岗位方向、职级、薪资、排除条件及最近确认日期 |
| `经历证据库.xlsx` | 可写入简历的真实经历、指标、ownership、来源及冲突状态 |
| `简历资产索引.xlsx` | 原始简历、岗位族底稿、每岗位唯一的定向简历资产及版本关系 |
| `品牌职位台账.xlsx` | 北京、上海、杭州、广州四城市岗位、唯一状态、深度结论、文件和下一步 |

## 初始化与读取

1. 先按精确文件名查找四项资产；存在时读取或本地化，不从 Skill 内的旧快照覆盖。
2. 缺失资产时，用用户已确认的简历、项目材料和搜索边界创建；事实冲突时只创建结构并把冲突标为待确认。
3. 每次写入保留原文件身份。匹配产物按下述版本清理规范处理：新版验收、正式登记成功后清理旧稿；写入失败时保留恢复所需文件，明确列出待回写字段，不声称已经更新。
4. 本契约只定义结构；用户事实只保存在共享资产及其可追溯来源中。

当前项目的正式台账固定为 `data/品牌职位台账.xlsx`。存在同名历史副本时不得仅按修改时间切换；除非用户明确迁移正式资产，否则继续更新这个文件。

## 匹配产物版本保留

若当前用户确认以下版本策略：每次匹配完成后只保留各岗位、各用途最新产物，删除已被替代的台账/索引副本、审阅稿、单岗位简历旧稿和多轮临时副本。具体范围、来源保护、临时回滚、发布门槛、逐文件清单与删除回读统一按 [当前版本与旧稿清理](../../tailor-job-application/references/current-version-retention.md) 执行。原始简历、岗位族底稿、证据库、完整能力库、JD/来源和已投递/面试材料保留；本规则不授权递归删除混合目录。

## 经历证据库

每条证据至少包含：

| 字段 | 规则 |
|---|---|
| 证据ID | 稳定唯一值 |
| 经历/项目 | 用户可识别的名称 |
| 事实陈述 | 不含推测的最小事实单元 |
| Ownership | 主导、负责、参与、协同或未知 |
| 指标/结果 | 数值与口径分开保存；无数据则留空 |
| 能力标签 | 品牌策略、IMC、GTM、IP、项目管理等 |
| 来源文件 | 原始简历或用户材料的文件名 |
| 来源位置 | 页码、段落或项目名 |
| 核验状态 | 已确认、用户确认底稿、用户原稿记载、既有简历细节记录、待回溯确认、待确认、冲突、不可用；保留来源性质 |
| 最近核验 | 日期 |

历史事实采用已确认记录及可定位用户原稿的一致记载；核对来源和上下文，无冲突时不反复确认。仅AI衍生的新细节及待回溯/待确认事项不自动晋升；冲突与不可用主张禁止写入。当前认知与方法按其依据积极表达，短期补不齐项从正式简历省略。

## 简历资产索引

| 字段 | 规则 |
|---|---|
| 资产ID | 稳定唯一值 |
| 文件名 | 与实际文件一致 |
| 层级 | 原始简历、岗位族底稿、单岗位定向副本 |
| 岗位方向 | 由真实内容归类，不预设固定数量 |
| 来源资产ID | 原始简历留空；其他版本指向直接父版本 |
| 关联岗位编号 | 仅单岗位定向副本必填 |
| 文件位置 | 可重新定位的持久文件引用 |
| 可编辑性 | 可编辑、需转换、仅供参考 |
| 事实核验状态 | 已核验、部分核验、待核验 |
| 最近更新 | 日期 |

原始简历永不覆盖。岗位族底稿只在存在稳定方向差异时建立；单岗位定向副本不得反向污染其他底稿。

每个岗位编号只能有一个当前有效的“单岗位定向副本”资产ID。首次生成时从底稿另存为新文件，不覆盖原始简历或岗位族底稿；用户后续无论修改多少轮，都在这一个岗位资产上持续迭代，保持资产ID、关联岗位编号和当前文件引用稳定，不反复创建“副本2/最终版3”等并行有效资产。每轮修改更新最近更新日期；新版验收、正式登记和回读通过后，按版本清理规范删除旧稿及本轮临时回滚副本，不再保留长期版本历史。

## 职位台账

`品牌职位台账.xlsx` 只允许四个工作表，顺序为北京、上海、杭州、广州。四表列结构完全一致，一条岗位只保留一条主记录。广州岗位编号使用 `GZ-` 前缀；天津不再进入搜索、统计或推荐范围。

### 唯一键与去重

优先使用来源职位 ID；缺失时使用：

`标准公司名 + 标准职位名 + 城市 + 规范化主链接`

重复来源写入备注或备用链接，不新增重复行。

### 多来源观察与收藏状态

脉脉、猎聘、BOSS直聘、51job、智联招聘、LinkedIn 和企业官网的观察结果写回同一岗位主记录，不建立第二套平台状态表。主链接优先企业官网；其他平台写入备用链接或备注。平台岗位 ID、收藏状态、平台流程状态、页面状态、分页范围和核验日期使用带平台名的结构化备注保存。

平台收藏只表示用户在该平台保存过岗位，不等于台账 `用户保留`，也不授权投递、沟通或修改外部状态。平台明确显示已投递、沟通或面试时，只补充证据且不得回退台账已有状态；平台明确显示职位关闭并且不存在投递历史时，可更新为 `已失效`。收藏消失、取消收藏或列表不可见不能单独证明岗位结束。

平台与台账证据冲突时保留各平台原文和核验日期，台账状态保持不变，并在“下一步”写一个会改变结论的冲突项。每轮临时来源覆盖清单只用于验收，完成后删除，不作为第二套职位台账。

### 招聘主体与公司情报

四个城市工作表统一增加并维护：

- `招聘主体类型`：`企业直招 / 猎头线索 / 招聘机构 / 匿名客户 / 待核实`。
- `企业招聘核验`：`同一企业职位已核验 / 仅发现相邻职位 / 未发现企业职位 / 企业未知 / 不适用`。
- `公司与岗位情报文件`：同岗位资料目录内稳定的 `公司与岗位情报.md` 引用。

详细招聘版图、经营/业绩、组织/汇报、竞品、岗位 scorecard 和来源清单保存在情报文件中，不在台账建立第二份研究报告。企业官网或企业认证职位为主链接；猎头和平台链接保留为备用来源。找到同一企业方职位时保持岗位编号和主记录稳定，不另建一条企业直招记录。

### 统一状态机

雷达主流程：

企业直招：

`新发现 → 公司情报核验中 → 深度评估中`

猎头、招聘机构或匿名客户线索：

`新发现 → 猎头线索核验中 → 公司情报核验中 / 已结束`

- 找到同一企业方职位：同一主记录改用企业方主链接，猎头链接转备用来源，再进入 `公司情报核验中`。
- 企业已识别但未找到同一企业方职位：`已结束`，结束原因写 `未找到同一企业方职位`。
- 企业身份无法核验：`已结束`，结束原因写 `猎头线索无法核验真实用人企业`。
- 已投递、HR 流程中或面试中的猎头岗位只补核验结果，不回退、不结束、不删除。

深度评估后只能进入：

- Apply：`待用户筛选`
- Pending：`待补材料`
- Skip：`深度评估后不投`

最终结论为 `Apply–P1/P2` 时，雷达自动生成该岗位唯一的 Word 审阅稿：

`待用户筛选 → 待用户筛选（审阅稿已生成）`

状态字段仍写 `待用户筛选`，同时在“定向简历资产ID/文件名”和“下一步”写明当前 Word 及“审核定向 Word 审阅稿”。审阅稿不是投递授权，也不得自动进入已投递状态。

最终结论为 `Apply–P3`、`Pending` 或 `Skip` 时不自动生成。用户在聊天中点名岗位，或在台账中手动把岗位状态改为 `用户保留` 并发出统一推进指令后：

`待用户筛选 / 待补材料 / 深度评估后不投 → 用户保留 → 定向材料已生成或保持用户保留并记录阻塞`

`用户保留` 表示用户已完成人工筛选并授权生成或继续维护该岗位投递资料，不再表示授权启动深度评估。它可以覆盖旧 Apply/Pending/Skip 的投递价值建议，但不能覆盖事实真实性；原 Pending/Skip 结论与风险必须保留。关键事实仍缺失时保持 `用户保留`，在下一步写入唯一阻塞项，不生成失真材料。

收到“处理台账里已保留的岗位”或等价指令时，扫描四表中状态精确等于 `用户保留` 的岗位。`待用户筛选` 和其他状态保持不变；已有唯一投递资料且没有新反馈时不得重复生成。

后续由用户或明确外部操作更新：

- `已投递—待反馈`
- `HR无回应或失联`
- `HR明确拒绝/不合适`
- `面试中`
- `已结束`
- `已失效`

用户明确筛选并确认不投时，状态保持 `深度评估后不投`，结束原因写 `用户确认不投`；不得改成 `已结束`，也不得同时维护第二套状态。自动深评得到的 `深度评估后不投` 只代表系统结论，不等于用户已确认终止。用户保存灰色终止设置后，在当前用户已有对应明确授权时在每周确认或雷达流程中执行清理；系统Skip本身不等于用户确认。

雷达和材料生成不得把 `已投递—待反馈`、`HR无回应或失联`、`HR明确拒绝/不合适`、`面试中`、`已结束` 或 `已失效` 回退为较早状态。

### 新鲜度重算

`首次发现` 是岗位第一次写入正式台账的日期，首次建立记录后永久保留，不因再次发现、复核、深评或状态变化而重置。每次雷达扫描、回写或重排都必须在处理所有岗位前，对四个城市表的全部数据行重算 `新鲜度`：

1. 以本轮 `Asia/Shanghai` 本地日期减去 `首次发现` 的本地日历日期，得到非负整数天数。
2. 统一写成精确的 `0天`、`1天`、`2天`……；不得保留“今日”“近7天”“90天内”等会随时间失真的静态文字。
3. `首次发现` 缺失、不可解析或晚于本轮日期时，`新鲜度` 写 `待核实`，保留原始值于备注并报告一个数据质量异常；不得猜测或反向使用发布时间补写。
4. `发布时间原文` 与 `标准发布日期` 继续描述招聘页面的发布证据；`新鲜度` 只表示岗位进入雷达后的入账天数，两者不得混用。
5. 灰色、结束、已失效及其他终态行同样重算。排序时使用重算得到的整数天数，数字越小越新；`待核实` 排在同组可计算值之后。

### 审阅稿与颜色信号

每个岗位只维护一个当前 Word：

1. 首屏明确标记 `审阅稿，不可直接投递`，随后写岗位元信息、来源 URL、获取/核验日期、完整性和缺失字段。
2. 放一页以内的公司/业务线情报摘要，包含主体、招聘版图、经营/业绩、组织/汇报、竞品、岗位 scorecard、来源编号、置信度和未知项。
3. 完整可核验 JD 在前；只能取得摘要时照录摘要并显著标记缺失，不得补写。
4. 显式分页后放定向简历。
5. 同岗位后续反馈或迁移更新同一当前文件，新版验收与正式登记成功后按版本清理规范删除被替代旧稿；不得产生多个并列“最新版”。
6. 批量迁移只处理允许继续操作的岗位；已投递、招聘流程中、终止、已失效或灰色岗位不迁移、不回退状态。

台账数据行颜色只作视觉信号，必须与状态、下一步和文件字段并用。每轮扫描、回写或重排时审计四个城市表的全部数据行，按 `灰色终止 > 用户反馈绿色 > 生成受阻淡红 > 审阅稿待审核淡黄 > 普通白色` 的优先级统一整行填充：

- 灰色 `#D9D9D9`：用户确认不投，或系统按契约完成猎头企业方核验后终止。
- 绿色 `#C6E0B4`：用户手工标记“已调整，等待系统吸收”。绿色不等于 `用户保留`、投递授权或外发授权。
- 淡红 `#F4CCCC`：生成失败或被一个关键缺失项阻塞。
- 淡黄 `#FFF2CC`：系统已生成新审阅稿，等待用户复核。
- 白色 `#FFFFFF`：没有上述信号的普通行。

仅统一数据行的状态填充，不改标题、表头、链接字体或其他非状态格式。现有浅蓝、其他灰色或未定义填充若没有独立业务含义，一律按上述映射恢复为对应颜色；不得保留第二套色号。同一行同时命中多个信号时只使用优先级最高的颜色。

处理绿色行时必须优先读取用户修改。只有成功吸收并更新同一岗位当前 Word 后，才清除绿色并改为淡黄；失败时保留绿色，在“下一步”写入唯一阻塞项，不用红色覆盖绿色。系统只清除自己能够证明已完成处理的绿色，不以颜色推测用户意图。

### 灰色终止岗位材料清理

当前用户另行明确授权后的执行规范统一见[文件包命名与每周终止清理](../../tailor-job-application/references/package-maintenance.md)。明确失效、HR无回应或失联及用户灰色终止岗位按新规范自动清理全部生成材料和单岗位索引，保留台账历史。旧的同范围逐次授权与投递历史保留限制由新规范替代；待反馈、面试中、用户保留及绿色冲突仍保护。目录使用 `岗位编号_公司_具体岗位名称`，清单精确核验岗位编号与实际目录。

### 雷达写入字段

岗位编号、状态、优先级、能力匹配区间、公司、职位、城市/区域、招聘主体类型、企业招聘核验、公司与岗位情报文件、来源、原始链接、备用链接、完整JD/快照、薪资原文、月薪上下限、年包上下限、月Base判断、薪资判断、发布时间、新鲜度、年限、团队管理、核心职责、硬门槛、最强初筛证据、主要风险、首次发现、最近核验、下一步、备注。

### 定向 Skill 回写字段

招聘主体类型、企业招聘核验、公司与岗位情报文件、最终结论、真实匹配区间、当前简历可见区间、定调后可达区间、最强证据、核心风险、选用底稿资产ID、定向简历资产ID/文件名、修改说明、首轮话术、投递前检查、协同核查问询文件、深度评估日期、状态、下一步、结束原因。

同一字段已有值时更新原字段，不另建近义列。

## 权限边界

- AI 可自主搜索、去重、排序、薪资归一化，并对所有通过雷达硬筛的岗位自动完成深度评估和台账回写。
- AI 可自主核验招聘主体、建立公司与岗位情报、反查猎头线索对应的企业方职位；猎头线索未找到同一企业方职位时不得进入深评或材料生成。
- AI 可在每轮雷达开始时，以及定向 Skill 处理具体岗位前，审计灰色终止候选。系统核验猎头终止在门槛全部满足时可自动清理；用户终止在当前用户已有对应明确授权时与文件包维护规范判断；不能仅凭系统 `深度评估后不投` 自动删除。
- AI 可按“系统核验猎头终止”协议结束、标灰并清理没有投递历史且未通过企业方核验的猎头岗位；台账事实行必须保留。
- 雷达深评为 `Apply–P1/P2` 且 JD 与已确认事实足够时，自动生成该岗位唯一 Word 审阅稿并标淡黄；生成受阻时不伪造文件，按颜色规则和唯一阻塞项降级。
- `Apply–P3`、`Pending` 与 `Skip` 不自动生成；用户人工写入 `用户保留` 或在聊天中明确点名后，才可按人工覆盖规则生成。
- 用户在台账中手动写入 `用户保留` 并发出推进指令，或在聊天中明确点名岗位，即授权生成或继续维护一套投递资料；不要求逐个复制编号。
- 人工保留可覆盖旧投递建议，但不得覆盖事实核验。AI 必须保留原风险，只从已确认素材和原始来源提取内容，并按每个 JD 独立定调。
- 允许在不改变事实含义的前提下有限补足情境、行动和结果逻辑；禁止无依据扩大 ownership、指标、预算、团队规模、职责范围、语言水平或能力熟练度。
- 定向简历必须符合选定底稿或用户确认模板的栏目、信息层级和主要版式。
- 公司情报摘要与 JD 前置容器仅供核查，不得直接投递；分页后的简历正文从首版起执行可直接投递质量标准。需要干净投递稿时，不以用户再次确认内容为前置；使用已有成稿标尺或正式模板更新同一当前资产，确保 JD 与来源已独立保存，新版验收与正式登记成功后按版本清理规范删除被替代的审阅版。投递或外发仍需单独明确授权。
- 按当前用户已确认的职业时间线和锁定段落写工作经历；保留真实任职性质、日期与职责，不使用其他候选人的固定经历或过渡期说明。
- 事实冲突、城市/薪资/职业方向改变必须询问用户。
- 禁止覆盖或删除原始简历、岗位族底稿和其他岗位当前资产。同一岗位被替代旧稿按版本清理规范处理；整个单岗位资料包及索引记录的删除仍须满足灰色终止清理协议。
- 每个岗位只维护一个当前定向简历资产；后续反馈修改该资产，新版验收与正式登记成功后清理旧稿，不新建并行有效副本。
- 禁止未经单独明确授权自动投递、发送消息或联系招聘方。

## 完整能力库与独立岗位说明

`经历证据库.xlsx` 继续作为结构化事实源，扩展能力索引、表述来源、来源清单和更新记录。`个人能力库.docx` 与 `.md` 是同源完整阅读/检索视图，覆盖全部经历、认知、个人实践和不同表述；不是某个JD的删选稿。具体结构与增量入口见定向 Skill 的 `references/capability-library.md`。

先读全库和同项目最新相关补充，按能力×岗位问题判断，再选模板。能力性质和事实核验状态分开；可说明的当前认知与方法不因没有同行业履历而无效。旧“用户确认底稿”枚举核对原件与确认依据后使用，不一律当缺失，也不无依据批量确认。

所有定向简历以争取首轮面试为目标。可短期整理的认知、方法和案例分析采用积极表达，真实项目贡献按实际判断、动作与负责环节充分扩写。短期补不齐内容从正式简历省略，不出现“已有理解、可迁移基础、正在补足”等内部标签。未参与项目不得编成经历；个人练习、模拟方案、实际商业项目分别标明性质。

每个定向材料包另维护一个岗位竞争力与快速补强说明 Word及同源Markdown，已有同目的文件直接升级。每岗唯一Word约束指当前定向简历，不禁止独立的个人准备说明与面试包。说明不作为另一份简历或第二套岗位状态，包含最核心竞争力、正文支撑、缺口、最短任务及验收。面试Skill读此说明和最终简历后生成八模块与逐条追问。
