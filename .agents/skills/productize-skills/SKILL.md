# Skill 产品经理

把 Skill 开发当作产品开发。先定义问题与验收方式，再实施；禁止从模糊想法直接跳到文件搭建。

## 总体原则

- 区分“使用现成 Skill”和“开发或改造 Skill”。只接管后者。
- 以 Skill 固化稳定专业能力，由 Agent 负责识别阶段、调用 Skill 和协调交接；不要仅为强化角色人设而重复封装已有的确定性专业流程。
- 优先读取用户提供的真实材料、旧 Skill、历史输出和失败案例，不让用户重复描述已有信息。
- 合并其他终端、云端或外部副本的规格时，把对方内容视为补丁：先审计本地当前实现和最近修改，再只合并缺失且不冲突的部分；不得假定外部副本更新、更完整或会自动同步，也不得整包覆盖本地 Skill。
- 先做风险分级，再决定走完整三步或快速通道；无法确定时走完整三步。
- 完整三步中的外部调研、内部访谈和产品定义确认都是开发门禁，不得用“信息似乎足够”代替。
- 区分两类调研：产品定义前的需求外部调研用于定义正确产品；产品定义确认后的 GitHub 开源调研用于选择实现路线，二者不得相互替代。
- 产品定义确认不自动授权开发。需要 GitHub 调研时，还必须提交技术路线与最简 MVP，并获得用户第二次明确确认。
- 每轮最多询问 3–5 个能改变方案的关键问题；已有材料可以预填答案、减少重复提问，但不能代替用户对最终产品定义的明确确认。
- 每一个 Skill 在正式启用前至少完成一轮真实任务试运行。
- 只创建实际需要的 `SKILL.md`、`agents/openai.yaml`、`scripts/`、`references/` 和 `assets/`，避免装饰性文件。

## 风险分级与路线

开始时先公开报告分类、理由与所选路线。

### 完整三步

以下任一情况成立时必须走完整三步：

- 新建 Skill。
- 重构现有 Skill 的目标、触发范围、输入输出、核心流程或文件架构。
- 复杂升级：改变 AI/人工决策边界、工具或权限、外部写入、失败降级、质量门、跨 Skill 串联，或引入新的高风险行为。
- 用户提出的“优化”含义不明确，尚不能证明只是机械修复。

完整三步为：外部调研 → 内部访谈 → 产品定义确认。确认前只允许读取、调研、分析和起草规格，不得创建或修改 Skill 文件、脚本、资源和安装状态。

产品定义确认后，按以下规则判断开发前 GitHub 调研：

- 新建 Skill：强制执行。
- 重构 Skill：强制执行。
- 复杂升级：先判断开源项目是否可能对本次实现提供实质帮助；有帮助才执行，并记录判断依据。
- 纯参数修改和确定性修复：不执行。

复杂升级出现以下任一特征时，优先判定为可能有实质帮助：新增前端、网站或交互界面；新增通用技术模块；新增自动化、数据处理或工作流能力；市场可能已有成熟工具或组件；复用可能显著降低开发、测试或维护成本。若只是修改 Skill 指令、规则或判断门槛，且开源代码无法实际参与实现，可跳过并记录理由。

### 快速通道

仅在变化完全确定且不改变产品行为边界时使用：

- 修改已确认的数字、名单、文案或其他参数。
- 修复错别字、失效链接、格式或确定性 Bug。
- 同步同一条已确认规则到遗漏位置。

若修改会影响触发条件、输入输出、流程顺序、AI/人工边界、工具权限、风险或验收标准，不得使用快速通道。快速通道仍须说明变更范围、验证受影响案例，并按 `skill-creator` 规范保存。

## 完整三步工作流

按顺序执行，不得跳步。已有材料只能作为阶段输入；只有可核验的同一版本产物才能复用，并须公开说明复用内容。外部调研必须先于正式内部访谈：不得先抛出 3–5 个产品问题，再承诺之后调研。

### 1. 受理与现状审计

确认直接用户、使用场景和期望价值。收集至少 2 个具体调用示例；复杂 Skill 优先收集 3–5 个，包括一个失败或边界案例。

检查现有 Skill、模板、参考资料、样例输入输出和用户已说明的规则，提炼：

- 当前做法及步骤
- 最慢、最烦、最容易出错的环节
- 必须保留的用户判断
- 已知失败模式和不可接受结果

不要把已经存在于材料中的问题重新问给用户。

本阶段优先从当前对话、现有文件和历史材料提取案例。若缺少现有 Skill 的位置、待分析材料或最小调研主题，导致无法开始只读审计或外部调研，只索取这一项阻塞材料；不要在此阶段提前提出产品访谈问题。

### 2. 外部调研门禁

- 新建或重构：调研成熟方案、最佳实践、类似工具或标准，带回 2–4 个真正不同的候选方案。
- 复杂升级：至少比较“当前方案＋1 个替代方案”；必要时扩展到 2–4 个方案。
- 比较适用条件、优势、局限、成本、风险和对本 Skill 的影响，给出推荐。
- 优先使用一手、官方或可核验来源；涉及会变化的工具和产品能力时验证当前信息。

只有不存在可用外部方案且已记录检索范围与结果时，才可把“无外部方案”作为调研结论；不得把主观判断写成“无需调研”。

### 3. 内部访谈门禁

完成并展示方案比较与推荐后，先整理 3–5 个真正影响架构的问题。已由用户确认材料回答的问题可以预填答案并请用户核对，只向用户追问其中仍未解决的问题。优先覆盖：

- 最终交付结果及其使用者是谁？
- 哪些输入一定存在，哪些可能缺失？
- 哪一步最慢、最容易出错或最需要用户经验？
- 哪些决定可以由 AI 自主完成，哪些必须询问或确认？
- 什么结果算成功，什么错误绝不能发生？

问题总数为 3–5 个，且必须体现调研结果带来的选择；不要问调研前就能自行查明的事实。答案足以决定架构后停止访谈，不为“完整”而继续提问。

### 4. 产品定义与确认门禁

使用 [产品定义与验收模板](references/product-definition-template.md) 形成精简规格，至少包含：

- 一句话目标
- 触发与不触发条件
- 典型调用示例
- 必要输入、可选输入和缺失信息处理
- 标准输出及质量要求
- 分步工作流与工具需求
- AI 自主决定、需告知、需确认的边界
- 失败模式、风险与降级方案
- 所需脚本、参考资料和资产
- 可观察、可执行的验收标准
- 试运行案例

先向用户提交这份产品定义并明确标记 `产品定义待确认`。只有用户明确表示“确认、按此推进、全部选 A”等足以指向该版本的同意后，才能进入 GitHub 调研或实质帮助判断；不需要 GitHub 调研时才可直接进入开发。沉默、回答访谈问题、提供材料或此前对零散规则的认可都不等于确认产品定义。

若用户要求调整产品定义，更新后重新确认。若发现过去已越过门禁，立即暂停开发，说明缺失阶段并补齐，不把已写文件当作既成事实迫使用户接受。

### 5. GitHub 开源方案与技术路线门禁

仅在产品定义已明确确认后执行。不得在本阶段之前写代码、创建实现脚本或修改 Skill；也不得把产品定义前的需求外部调研冒充本阶段调研。

#### 5.1 判断是否进入调研

- 新建和重构：直接进入调研。
- 复杂升级：依据“实质帮助”标准判断。进入时继续本阶段；跳过时公开记录理由，并可进入设计开发。
- 快速通道：不进入本阶段。

#### 5.2 搜索与筛选

- 在 GitHub 搜索并比较 2–4 个与已确认产品定义真正相关的项目；不足 2 个时说明检索词、范围和无合适候选的结果。
- 核验仓库链接、近期提交或 Release、Issue/PR 活跃度、许可证、技术栈、依赖与安全风险、部署难度和二次开发成本。
- 不用 Star 数单独判断质量或维护状态，不把无法核验的假设写成事实。
- 逐项对照产品定义的核心功能、运行环境、权限边界与验收标准；明确可直接复用、需要改造、仅能参考设计和无法覆盖的部分。

#### 5.3 按顺序选择技术路线

1. **直接使用**：仅当候选项目完整满足全部核心功能，且许可证、维护状态、安全性、部署复杂度和运行环境均可接受时推荐。大部分相似但仍缺核心功能，不得推荐直接使用。
2. **基于现有项目二次开发**：候选无法完整满足产品定义，但代码或架构有真实复用价值、改造成本低于自研、许可证允许，且不会为迁就旧项目牺牲核心需求时优先推荐。若只能借鉴思路，明确写“参考设计后自研”，不要虚称二次开发。
3. **完全自行开发**：仅在无合适项目、核心需求冲突、改造成本不低于自研、维护或许可证不合适、安全风险不可接受，或部署依赖不适合最简 MVP 时推荐。

#### 5.4 提交技术路线与最简 MVP

向用户提交：

- 2–4 个候选项目及链接；不足时说明检索范围。
- 维护状态、许可证、部署和依赖复杂度。
- 与产品定义的逐项匹配表。
- 可直接复用、需改造、仅供参考和无法覆盖的部分。
- `直接使用 / 基于现有项目二次开发 / 完全自行开发` 的唯一推荐结论与理由。
- 最简单可验证 MVP：包含、不包含、预计复用比例、主要风险和验证方法。

明确标记 `技术路线待确认`。只有用户明确同意该技术路线与 MVP，才能开发；回答补充问题、认可某个候选项目或沉默均不等于授权。用户要求调整时，更新提案并重新确认。

### 6. 设计并开发

遵循 `skill-creator` 的创建或更新规范实施：

- 保持 `SKILL.md` 精简，写核心流程和资源路由。
- 把详细知识、模板和长示例放入 `references/`。
- 把重复、确定性或高风险操作放入可测试的 `scripts/`。
- 把输出所需模板、品牌材料或样板放入 `assets/`。
- 在 description 中写清“做什么”和“何时触发”，不要依赖正文解释触发条件。
- 根据任务脆弱程度设置自由度：判断型流程给原则，稳定重复流程给脚本，易出错流程给严格门禁。

### 7. 校验与试运行

先做结构校验，再执行真实案例试运行。试运行至少覆盖：

1. 一个典型成功案例
2. 一个输入缺失、模糊或异常案例
3. 一个触发边界案例，验证不该触发时不会误触发

复杂 Skill 还要覆盖高风险失败模式。记录每个案例的输入、实际行为、结果和问题，不把解释或预期答案泄露给独立测试者。

发现问题后区分：

- 产品定义问题：回到第 4 或第 5 阶段。
- Skill 指令或资源问题：回到第 6 阶段。
- 单次执行问题：修正后重跑失败案例及相关回归案例。

所有硬性验收标准通过后，才标记为“可正式启用”。

### 8. 交付与调用说明

向用户说明：

- Skill 解决什么问题
- 哪些说法会触发它
- 1–3 条可直接复制的调用示例
- 哪些情况不会触发
- 试运行是否通过及仍有哪些限制

若尚未通过试运行，明确标记为“试用版”，不要称为正式完成。

## 全局强制触发规则

凡是用户要求新建、生成、创建、固化或沉淀一个新的 Skill，必须先进入本 Skill 的完整产品化流程。不得直接调用 `skill-creator` 创建文件后再补流程，也不得因为需求看似简单、用户曾经提过、已有类似 Skill 或上下文中已有方案而跳过外部调研、内部访谈和产品定义确认。

在产品定义获得用户明确确认前，只允许进行需求受理、现状审计、风险分级、外部调研、内部访谈和产品定义草案；不得创建或修改目标 Skill 的正式文件、脚本、资源、安装状态或启用状态。产品定义确认后，才可进入 GitHub 调研、实质帮助判断，或在不需要 GitHub 调研时直接进入开发。

产品定义确认后，新建与重构必须先进入 GitHub 开源方案调研，复杂升级必须先完成实质帮助判断。需要调研时，在用户明确确认技术路线与最简 MVP 前不得开发；只有确认技术路线后，才可进入开发、结构校验和真实试运行。复杂升级经记录确认开源代码无实质帮助时，可跳过 GitHub 调研进入开发。快速通道不触发 GitHub 调研。

如果用户没有明确说“新建 Skill”，但请求会改变现有 Skill 的目标、触发范围、输入输出、核心流程、工具权限、失败降级、质量门槛或跨 Skill 协作，也必须按完整流程处理。只有已确认边界内的确定性参数修改或机械性 Bug 修复，才可使用快速通道，并在开始前说明为什么不改变产品定义。

每次正式启用前，必须完成至少一轮真实任务试运行，并覆盖一个典型成功案例、一个输入缺失或异常案例和一个触发边界案例；未完成时只能标记为“试用版”，不能称为正式完成。新建与重构还必须验收 GitHub 调研、逐项匹配、技术路线与最简 MVP 的明确确认；复杂升级必须验收实质帮助判断及其记录。

## 快速通道工作流

1. 说明为何属于纯参数或确定性修复，并列出不会改变的产品边界。
2. 明确不进入 GitHub 调研，读取所有受影响文件，定位唯一事实来源和同步位置。
3. 实施最小修改，不顺带重构。
4. 运行结构校验，并回归一个受影响案例和一个邻近边界案例。
5. 按 `skill-creator` 规范保存，报告修改和验证结果。

执行中一旦发现修改会改变架构或风险，立即停止快速通道，转入完整三步。

## 阶段状态

在长任务中使用以下状态，避免把讨论误认为已经开发：

- `需求探索中`
- `产品定义待确认`
- `开源方案调研中`
- `技术路线待确认`
- `开发中`
- `快速修复中`
- `试运行中`
- `可正式启用`
- `待迭代`

每次更新只报告当前阶段、已完成产物和下一个动作。
