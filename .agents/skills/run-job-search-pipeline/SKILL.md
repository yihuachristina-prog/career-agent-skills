## 可迁移发行包的配置规则

先读取仓库中的 `docs/PORTABILITY.md`（或安装时一并保存的该文档）。这是导出包的参数适配层，优先于下文原项目限定与历史措辞。每个用户使用独立工作区和唯一资产库；真实姓名、职业时段、工资阈值、城市、资料路径及历史确认只从当前用户资料读取。原项目的常设授权不随 skills 转移：未记录当前用户对应清理授权时，仅生成清理建议，不执行删除。不得根据本包的历史日期推定当前用户已经确认。



## 2026-09-22 已确认的增量执行要求

沿用现有入口与资产。写作时执行[历史纠正对照](../tailor-job-application/references/candidate-writing-style.md)和[交付前检查](../tailor-job-application/references/resume-content-quality-gate.md)；雷达执行[信息缺失与连续跟进](../discover-brand-roles/references/search-profile.md)。这些规则优先于下文冲突的旧表述；保持搜索覆盖及既有底线，不加评分/未知即淘汰门。改稿前定位问题和必要范围，同岗保护最新确认段落，跨岗不继承局部条数、公司名或项目顺序。材料生成、文件检查、用户认可和实际投递分开记录；文件与台账写回分别回读，失败保持原状态及可恢复产物。历史认可样例只读保留。


## 文件包命名与每周清理（2026-09-14）

生成、定位、调整材料包或运行每周确认/雷达时，先执行[文件包命名与每周终止清理](../tailor-job-application/references/package-maintenance.md)。目录统一为 `岗位编号_公司_具体岗位名称`，编号保持稳定。仅在当前用户已有对应明确授权时，才可按已保存台账清理明确失效、HR无回应或失联、用户灰色终止岗位的全部生成材料，仅保留台账历史；本节覆盖下文旧的同范围清理限制，不要求每次重复授权。活跃状态、绿色冲突与原始资料按新规范保护。


## 用户限定的只读比较与历史演练

用户明确要求“仅比较/历史JD演练/只按给定材料做内容匹配、不搜当前岗位、不写库”时，直接使用已有材料做限定范围分析。标明材料时点、摘要/完整JD及未披露项；不触发实时公司核验、招聘状态结论、Word生产门或共享资产写入。照常输出能力×岗位问题、首屏与正文建议、最快准备；信息不足只限制相关结论，不阻塞已能完成的内容。转为正式定向材料或需要当前岗位结论时，再补齐相应情报与版本门。


# 求职流程总控

只负责识别阶段、维护交接和调用专业 Skill；不复制职位检索、简历修改或面试准备的内部逻辑。每个岗位独立推进，不要求整批岗位处在同一阶段。

## 全流程共同目的

所有定向简历为尽快获得首轮面试服务。先读完整个人能力库和同项目最新相关补充，以能力×岗位问题匹配；首屏与正文共同支撑为什么是我。相关规则由定向 Skill 的 [能力库](../tailor-job-application/references/capability-library.md) 和 [竞争力与补强](../tailor-job-application/references/why-me-and-readiness.md) 统一维护。短期补不齐的项从正式简历省略，成熟度判断仅在内部说明。

## 阶段与路由

| 阶段 | 触发信号 | 调用 |
|---|---|---|
| 0. 个人能力库 | 汇总全部简历、更新能力/经历/表达 | `$tailor-job-application` 能力库模式，无需JD |
| 1. 职位发现与主体核验 | 找工作、搜机会、跑职位雷达、定时更新 | `$discover-brand-roles` 区分企业直招与猎头线索；猎头先反查企业方职位 |
| 2. 公司情报、深评与P1/P2审阅稿 | 企业直招或已核验企业方职位 | `$tailor-job-application` 先建立公司/业务线情报，再深评；P1/P2同轮生成唯一 Word 审阅稿 |
| 3. 用户复核与人工保留 | 审核淡黄新稿、绿色标记已调整；或把P3/Pending/Skip改为 `用户保留` | 吸收绿色反馈；人工保留项进入材料阶段 |
| 3a. 用户确认不投 | 用户已保存终止设置并发出处理/清理指令 | 保持 `深度评估后不投`，调用 `$discover-brand-roles` 标准化灰色、置底并按安全门槛清理 |
| 4. 定向材料 | 调整简历、准备投递、写打招呼、继续修改 | 先刷新情报，再由 `$tailor-job-application` 在同一当前 Word 上迭代 |
| 5. 用户验收 | 用户确认简历满意，或提出继续修改 | 不满意则返回阶段 4；满意后锁定版本 |
| 6. 投递 | 用户自行投递，或告知已投递 | 记录渠道、日期、版本和状态 |
| 7. 面试准备 | 收到面试、准备问题、模拟面试 | `$prepare-job-interview` |
| 8. 复盘 | 面试结束、收到反馈或结果 | 更新问题库、证据与下一步 |

不要让总控递归调用自身。

## 运行原则

### 1. 先识别用户真正要做的事

用户只要说出明确行动，例如“帮我搜今天的岗位”“处理台账里已保留的岗位”“给这个 JD 改简历”“明天面试”，就直接路由到相应 Skill。不要要求用户记忆 Skill 名称、逐个复制岗位编号或使用特殊唤醒词。

用户显式输入 `$discover-brand-roles`、`$tailor-job-application` 或 `$prepare-job-interview` 时，尊重其选择。

### 2. 每个阶段设置人工门

以下动作必须等待用户明确决定：

- `Apply–P3`、Pending、Skip 从深评进入定向材料：用户写入 `用户保留` 或在聊天中明确点名。
- 系统自动 Skip 不自动成为用户终止；清理资格与每周常设授权按文件包维护规范判断。
- 从定向简历进入投递：用户确认文件满意并决定投递。
- 对外发送消息或提交申请：用户明确要求执行，并在执行前核对目标。

`Apply–P1/P2` 可自动生成审核用 Word，不需要用户先保留；这只减少初稿操作，不等于用户决定投递。可以自动完成内部分析、文件生成、问题预测和状态更新，但不得把“用户可能会喜欢”当作同意投递。

自动生成还有公司情报门：企业身份、岗位存在性和核心 JD 必须可核验。猎头/招聘机构/匿名客户线索只有找到同一企业方职位后才能进入深评和材料阶段；未找到时结束并按共享契约清理无投递历史的单岗位材料。

台账中的 `用户保留` 是用户人工筛选结果，可覆盖 AI 原有 Apply/Pending/Skip 的投递价值建议；覆盖不等于允许改写事实。原结论为 Pending/Skip 时必须保留风险提示，关键事实仍缺失时暂停材料生成并把唯一阻塞项写入原行。

### 3. 维护最小状态

每个岗位保留：

- 岗位编号、公司、职位、城市、来源链接
- 当前阶段与优先级
- 使用的简历版本、能力库版本、独立竞争力与快速补强说明、正文支撑映射及补强产物状态
- 招聘沟通话术版本
- 投递渠道与日期
- 面试轮次、时间、反馈
- 下一步和阻塞项

优先在职位雷达工作簿原记录中更新，不建立多个互相冲突的台账。

收到“处理台账里已保留的岗位”或等价指令时：

1. 按共享数据契约定位当前项目唯一正式台账，不按修改时间在同名副本间猜测。
2. 扫描北京、上海、杭州、广州四个工作表，处理状态精确等于 `用户保留` 的岗位和等待吸收的绿色当前资产。
3. 已有唯一投递资料且用户没有新反馈时不重复生成；尚无资料的岗位分别交给 `$tailor-job-application`。
4. 普通 `待用户筛选`、`待补材料`、`深度评估后不投` 等其他状态保持不变。
5. 汇总已生成、已存在、因关键事实阻塞和失败待回写的岗位。

收到清理、每周确认调整或雷达运行指令时，按文件包维护规范扫描唯一台账，处理已授权终态；保留历史主记录，并回读验证精确清理结果。

### 4. 使用版本门

完成匹配、材料迭代和正式回写后，统一执行 [当前版本与旧稿清理](../tailor-job-application/references/current-version-retention.md)。只清理已验收被替代的匹配产物及本轮临时副本；原始资料、JD、证据库和已投递/面试材料保留。失败时保留恢复所需文件，报告精确阻塞，不以删除尝试数冒充成功数。

- 职位雷达使用最新确认的共享画像与经历证据；简历作为多资产池保留，不指定唯一通用母版。
- 定向简历比较所有可用原始简历和岗位族底稿；用户指定版本时优先。不同 JD 分别生成独立定向副本，不覆盖或反向污染其他版本。
- 每个岗位只维护一个当前定向简历资产。首次从底稿另存，后续所有反馈修改这一个资产；新版验收与正式登记成功后清理旧稿和临时副本，不反复创建平行副本。
- 当前审阅稿统一为 `公司/业务线情报摘要 → 完整可核验 JD → 显式分页 → 定向简历正文`；公司推断和来源不得混入简历正文。需要干净投递稿时更新同一当前资产，JD 与来源独立保存后，按版本清理规范删除被替代的旧审阅稿。
- 用户绿色只表示“已调整，等待吸收”。成功吸收后绿色转淡黄；失败时保留绿色并写一个阻塞项。
- 每个岗位根据自己的 JD、深评证据和风险单独定调；不得把同一套关键词或改写机械套用到多个岗位。
- 只从已确认的经历证据库、原始简历和可追溯项目材料提取事实。允许为清晰度补足情境、行动和结果关系，但不得扩大 ownership、指标、职责范围或能力熟练度。
- 定向简历必须沿用选定底稿或用户确认模板的内容结构和版式；无法可靠保留时先降级说明，不得交付脱离模板的空白重写稿。
- 每次生成或实质更新定向简历，检查独立竞争力与快速补强说明同步交付且复用现有同目的资产；核心主张、正文位置和面试口径一致。同步更新该岗位的协同核查问询，供用户自行交给其他模型复核；总控不自动发送。
- 面试准备只使用用户确认满意的最终定向简历。
- 用户上传新定版简历并指令入库时，交定向 Skill 增量吸收新事实、实践与表述；仅比较不写库。保持其他岗位历史投递版本不变。

### 5. 处理返回与循环

允许正常回退：

- 用户认为岗位不合适：回到职位发现。
- 用户对简历不满意：留在匹配与定向，按反馈迭代。
- 面试问题暴露简历主张不准确：暂停面试准备，回到定向简历纠正事实，再重新准备。
- 搜索规则发生变化：先更新职位雷达画像，再运行新一轮。

循环必须有原因和版本变化；不得在用户没有新反馈时反复重写同一份简历。

## 默认完整运行

用户说“跑完整流程”但没有指明阶段时：

1. 检查是否已有完成深评的最新职位雷达。
2. 没有则调用 `$discover-brand-roles`。
3. 对企业直招或已找到同一企业方职位的岗位完成公司/业务线情报门；未通过企业方核验的猎头线索结束。
4. 展示深评后的 Apply、Pending、深评淘汰和猎头核验摘要，不把初筛分数当最终结论。
5. 对 `Apply–P1/P2` 提供已生成的淡黄 Word 审阅稿；对 P3/Pending/Skip，用户标记 `用户保留` 或直接点名后再调用 `$tailor-job-application`。
6. 用户把修改后的行标绿时，先刷新会改变结论的公司情报，再调用 `$tailor-job-application` 吸收反馈、更新同一当前 Word，成功后转淡黄。
7. 等待用户确认满意与实际投递状态。
8. 收到面试或用户主动要求后调用 `$prepare-job-interview`。

## 当次输出

每次只告诉用户：

- 当前处于哪个阶段
- 本次完成了什么
- 下一个必须由用户决定的动作
- 下一步会调用哪个专业 Skill

若某专业 Skill 因输入不足而暂停，准确列出唯一关键缺失项，不重新进行整套访谈。

## 质量门

- 单一专业请求没有被总控复杂化。
- 职位、简历、沟通话术与面试材料使用同一岗位编号和版本。
- 人工筛选、简历验收和外部投递三个门没有被绕过。
- 通过雷达硬筛的岗位已自动深评；初筛通过但深评 Skip 的岗位没有静默消失。
- 进入深评的岗位已通过招聘主体和公司情报门；猎头线索未找到同一企业方职位时没有进入材料阶段。
- 雷达只为 `Apply–P1/P2` 自动生成审阅稿；未选中的 P3/Pending/Skip 没有误生成。
- 台账批量入口只处理 `用户保留` 和明确的绿色反馈，其他未筛选岗位没有被误处理。
- 已授权的每周终止清理按文件包维护规范执行；系统自动Skip与活跃状态冲突未被误删。
- 用户人工保留可以覆盖旧投递建议，但不能绕过事实核验、模板验收或外部投递确认。
- 同一岗位的多轮修改保持唯一当前投递资料资产；新版验收、正式登记成功后清理被替代版本，并核验源路径消失、保留文件哈希与恢复状态。
- 不同岗位根据各自 JD 独立定调，没有批量套写。
- 不同岗位根据各自公司/业务线情报、岗位 scorecard 和 JD 独立定调；公司推断没有被写成候选人事实。
- 简历表述全部可追溯，有限扩写没有扩大经历事实，最终文档符合选定简历模板。
- 生成或更新定向简历后已同步提供协同核查问询，但未自动调用外部模型。
- 没有自动联系招聘方或自动投递。
- 循环有明确反馈，不发生无意义重复调优。
- 用户用自然语言即可推进，不依赖界面中是否显示 Skill 字样。
